# AGENTS.md — інструкція для ШІ-агента учасника команди

Цей файл — для ШІ-агента, який допомагає
**одному конкретному учаснику команди** локально налаштувати і реалізувати
його частину цього STEM-проєкту. Прочитай його повністю, перш ніж
торкатися коду.

## 0. Перше, що треба зробити

Запитай людину, з якою ти працюєш: **яке її ім'я / GitHub-логін** і
**який номер учасника** (`member1`, `member2` чи `member3`) вона отримала
від команди (див. таблицю в [TZ.md](TZ.md)). Усе нижче описано через
`memberN` — підставляй конкретне значення.

Якщо заміна `member1`/`member2`/`member3` на реальні імена ще не зроблена
ніким у команді — **не роби її сама(сам) наодинці**: це торкається
`src/`, `tests/` і `TZ.md` одразу для всіх трьох, і краще зробити одним
узгодженим PR, щоб не зіткнутися з конфліктами. Спитай людину, чи вже
узгоджено, хто це робить.

## 1. Що це за проєкт

STEM-проєкт (методичка з обробки зображень класичними методами, без
ML/нейромереж у самих алгоритмах). Повний опис — [README.md](README.md),
технічне завдання з розподілом методів по людях — [TZ.md](TZ.md). ТЗ —
**чернетка**, яку команда ще узгоджує з викладачем; не вважай цифри й
домен вибірки в ньому остаточними.

## 2. Локальне налаштування

```bash
python -m venv .venv
source .venv/bin/activate   # Windows: .venv\Scripts\activate
pip install -r requirements.txt
python -m pytest -q
```

Усі 22+ тести спільної інфраструктури мають проходити одразу після
клонування — якщо ні, це баг у `common/`, а не в твоїй частині; повідом
команду, не намагайся "тихо" це обходити.

## 3. Межі твоєї зони

- **`src/<твій-member>/pipeline1/` і `pipeline2/`** — твоя особиста зона.
  Тут ти працюєш вільно.
- **`src/member<інший>/...`** — НЕ торкатися без прямого прохання тієї
  людини.
- **`common/`** — спільна інфраструктура команди (блок C, однакова оцінка
  для всіх трьох). Зміни тут — тільки через PR з рев'ю від когось іншого
  з команди, навіть дрібні.
- **`config/pipelines.yaml`** — можна редагувати параметри ТІЛЬКИ своїх
  двох пайплайнів (секції `memberN.pipeline1` / `pipeline2`).
- **`TZ.md`, `README.md`, `.gitignore`, `pytest.ini`, `requirements.txt`**
  — спільні файли; зміни тут узгоджувати з командою, не редагувати
  мовчки під час роботи над власним пайплайном.

## 4. Що саме реалізувати

У `src/<твій-member>/pipelineN/stage_*.py` кожен файл має заглушку:
`apply(image, **params) -> Image.Image`, яка зараз просто повертає
зображення без змін. Докстрінг кожного файлу називає категорію методу і
дає підказку — заміни реалізацію на справжній алгоритм із цієї категорії
(категорії й конкретні методи — у таблиці в [TZ.md](TZ.md), розділ
«Методи та категорії»).

Правила реалізації (із методички):

- Лише ручна реалізація алгоритму. Бібліотеки (Pillow, numpy) — тільки
  для вводу/виводу, базової математики (FFT, cumsum тощо) чи типів даних,
  **не** для самого методу (ніяких `cv2.Sobel`, `scipy.ndimage.filters`,
  готових `PIL.ImageFilter` для твого основного алгоритму).
- Усі параметри — через `config/pipelines.yaml`, не хардкодь у коді.
- Якщо є випадковість — фіксований `seed`.
- Пайплайн має виконуватись автоматично, без ручного втручання між
  стадіями.
- Обробити межові випадки без аварійного завершення (порожній/малий
  файл, grayscale) — список у TZ.md, розділ «Межові випадки».

## 5. Тести (критерій C3)

У `tests/<твій-member>/test_pipelineN.py` вже є шаблон із двома тестами
проти заглушки. Коли реалізуєш справжній метод — заміни
`test_apply_matches_stub_behaviour` на тест із **вручну порахованим**
очікуваним результатом на маленькому (3×3–5×5) зображенні. Це не
формальність: саме це перевіряють на захисті.

## 6. Академічна доброчесність і робота з ШІ — важливо

Можна користуватися тобою (ШІ-агентом) для реалізації. Але є жорсткі
умови з методички, які прямо впливають на оцінку:

1. **Кожне використання ШІ фіксується** у [META-USAGE.md](META-USAGE.md),
   у секції свого учасника: дата, інструмент, файл/функція, суть запиту,
   що згенеровано vs написано самостійно. Недекларований ШІ-результат —
   штраф (множник M = 0,5) на весь проєкт команди, не лише на твою
   частину.
2. На захисті людину попросять **наживо змінити власний код** і пояснити
   кожен рядок. Тобто: перш ніж комітити згенерований тобою код, людина
   має його прочитати, зрозуміти й бути здатна відтворити логіку без
   тебе. Твоя задача як агента — не просто видати робочий код, а
   переконатися, що людина його розуміє (поясни логіку, не лише покажи
   diff).
3. Не редагуй `META-USAGE.md` мовчки за людину — запропонуй текст запису,
   але нехай людина підтвердить, що це описує саме те, що відбулося.

## 7. Git-workflow

- Працюй у гілці `feature/<ім'я>-pipelines`, не в `main`.
- Коміти — дрібні, по завершеній стадії (`feat(member2): add Gaussian
  blur stage`), без фіктивних повідомлень типу "update"/"fix".
- PR у `main` — навіть для власної зони (простіше для рев'ю й для
  "персоналізованої історії комітів", критерій A1).
- Ніколи не форсуй `common/` без узгодження і не перезаписуй чужі коміти
  (`git push --force` на спільні гілки — заборонено).

## 8. Якщо щось незрозуміло

Не вигадуй відсутні деталі ТЗ (порогові метрики, остаточний домен
вибірки) — вони чернетка й узгоджуються з викладачем. Якщо щось потрібне
для роботи відсутнє або суперечить іншому файлу — запитай людину, а не
вирішуй самостійно за всю команду.
