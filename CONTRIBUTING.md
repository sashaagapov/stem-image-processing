# Інструкція для нового учасника команди

Налаштування й правила роботи для кожного з трьох учасників цього
STEM-проєкту. Прочитайте перед тим, як торкатися коду.

## 0. Перше, що треба зробити

Визначте: **ваше ім'я / GitHub-логін** і **номер учасника** (`member1`,
`member2` чи `member3`), який ви отримали від команди (див. таблицю в
[TZ.md](TZ.md)). Усе нижче описано через `memberN` — підставляйте своє
значення.

Якщо заміна `member1`/`member2`/`member3` на реальні імена ще не зроблена
ніким у команді — **не робіть її наодинці**: це торкається `src/`,
`tests/` і `TZ.md` одразу для всіх трьох, і краще зробити одним
узгодженим PR, щоб не зіткнутися з конфліктами. Уточніть із командою, хто
це робить.

## 1. Що це за проєкт

STEM-проєкт (методичка з обробки зображень класичними методами, без
ML/нейромереж у самих алгоритмах). Повний опис — [README.md](README.md),
технічне завдання з розподілом методів по людях — [TZ.md](TZ.md). ТЗ —
**чернетка**; не вважайте цифри й домен вибірки в ньому остаточними, якщо
команда їх ще обговорює.

## 2. Локальне налаштування

```bash
python -m venv .venv
source .venv/bin/activate   # Windows: .venv\Scripts\activate
pip install -r requirements.txt
python -m pytest -q
```

Усі 22+ тести спільної інфраструктури мають проходити одразу після
клонування — якщо ні, це баг у `common/`, а не у вашій частині; повідомте
команду.

## 3. Межі вашої зони

- **`src/<ваш-member>/pipeline1/` і `pipeline2/`** — ваша особиста зона.
  Тут ви працюєте вільно.
- **`src/member<інший>/...`** — НЕ торкатися без прямого прохання тієї
  людини.
- **`common/`** — спільна інфраструктура команди (блок C, однакова оцінка
  для всіх трьох). Зміни тут — тільки через PR з рев'ю від когось іншого
  з команди, навіть дрібні.
- **`config/pipelines.yaml`** — можна редагувати параметри ТІЛЬКИ своїх
  двох пайплайнів (секції `memberN.pipeline1` / `pipeline2`).
- **`TZ.md`, `README.md`, `.gitignore`, `pytest.ini`, `requirements.txt`**
  — спільні файли; зміни тут узгоджуйте з командою, не редагуйте
  мовчки під час роботи над власним пайплайном.

## 4. Що саме реалізувати

У `src/<ваш-member>/pipelineN/stage_*.py` кожен файл має заглушку:
`apply(image, **params) -> Image.Image`, яка зараз просто повертає
зображення без змін. Докстрінг кожного файлу називає категорію методу і
дає підказку — замініть реалізацію на справжній алгоритм із цієї категорії
(категорії й конкретні методи — у таблиці в [TZ.md](TZ.md), розділ
«Методи та категорії»).

Правила реалізації (із методички):

- Лише ручна реалізація алгоритму. Бібліотеки (Pillow, numpy) — тільки
  для вводу/виводу, базової математики (FFT, cumsum тощо) чи типів даних,
  **не** для самого методу (ніяких `cv2.Sobel`, `scipy.ndimage.filters`,
  готових `PIL.ImageFilter` для вашого основного алгоритму).
- Усі параметри — через `config/pipelines.yaml`, не хардкодьте у коді.
- Якщо є випадковість — фіксований `seed`.
- Пайплайн має виконуватись автоматично, без ручного втручання між
  стадіями.
- Обробіть межові випадки без аварійного завершення (порожній/малий
  файл, grayscale) — список у TZ.md, розділ «Межові випадки».

## 5. Тести (критерій C3)

У `tests/<ваш-member>/test_pipelineN.py` вже є шаблон із двома тестами
проти заглушки. Коли реалізуєте справжній метод — замініть
`test_apply_matches_stub_behaviour` на тест із **вручну порахованим**
очікуваним результатом на маленькому (3×3–5×5) зображенні. Це не
формальність: саме це перевіряють на захисті.

## 6. Академічна доброчесність і використання ШІ-інструментів

Користуватися інструментами-помічниками (у тому числі ШІ) для
реалізації можна. Але є жорсткі умови з методички, які прямо впливають
на оцінку:

1. **Кожне використання ШІ повідомляється викладачці напряму** (словами,
   не файлом у репозиторії) — чи користувались, яким саме інструментом і
   для чого. Недекларований ШІ-результат — штраф (множник M = 0,5) на
   весь проєкт команди, не лише на вашу частину.
2. На захисті вас попросять **наживо змінити власний код** і пояснити
   кожен рядок. Тобто: перш ніж комітити згенерований код, прочитайте й
   зрозумійте його настільки, щоб відтворити логіку без підказки.

## 7. Git-workflow

- Працюйте у гілці `feature/<ваше-ім'я>-pipelines`, не в `main`.
- Коміти — дрібні, по завершеній стадії (`feat(member2): add Gaussian
  blur stage`), без фіктивних повідомлень типу "update"/"fix".
- PR у `main` — навіть для власної зони (простіше для рев'ю й для
  "персоналізованої історії комітів", критерій A1).
- Ніколи не форсуйте `common/` без узгодження і не перезаписуйте чужі
  коміти (`git push --force` на спільні гілки — заборонено).

## 8. Якщо щось незрозуміло

Не вигадуйте відсутні деталі ТЗ (порогові метрики, остаточний домен
вибірки) — вони ще чернетка. Якщо щось потрібне для роботи відсутнє або
суперечить іншому файлу — питайте команду.
